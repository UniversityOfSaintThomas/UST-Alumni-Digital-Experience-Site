    Portal Widget Authoring Experience — Implementation Plan¶

    Status: Phases A, 0–3 done. Phase 4 (hero widget + S3) is built; real uploads await the S3 credential. (Phases 0–2 committed by the owner; Phases 3–4 not yet committed.) Recorded so context survives a session reset. Created: 2026-10-14. Dev org: UST-Alumni-Digital-Experience-Site__dev (CCI alias dev), expires 2026-10-27.

    Goal¶

    Give portal admins a purpose-built authoring layout for UST_Portal_Widget__c (replacing the classic page layout) with a rich text editor that behaves like the Experience Builder one, plus the things clients actually need in widget content: call-to-action buttons, personalization data tags, and later a hero image widget backed by the S3 upload tool.

    Guiding decision: structured data beats markup in the rich text. Buttons are JSON on the record and rendered by our component (not HTML/classes inside Quill). That removed the need for a custom Quill build and for a per-paragraph class list.

    Gotchas learned (do not re-discover)¶

    • lightning-input-rich-text limits. Allowed formats include header/link/image/code/blockquote/ script/direction/table, but toolbar buttons exist only for bold/italic/underline/strike, lists, indent, left/center/right align, link, image, clear. setFormat() only accepts align, background, bold, code, code-block, color, font, header (1–6), italic, link, size, strike, underline. No access to the Quill instance, modules, registries, or selection events. class attributes cannot round-trip.
    • getFormat() steals focus. It refocuses the editor, closing the heading dropdown and the Link dialog. Cursor-sync handlers are on a wrapper around only the rich text, and toolbar clicks (clientY < TOOLBAR_HEIGHT_PX) pause tracking for 8 s (TOOLBAR_PAUSE_MS). composedPath() does not expose .ql-editor, so geometry is the only way to tell toolbar from text.
    • Combobox change bubbles out of the child component and was mistaken for a content change ("h3" replaced the body). Both handlers call event.stopPropagation().
    • The editor textbox only exists after a real mouse click in the editor area (lazy init) — matters for Playwright tests.
    • Stale Lightning bundles after a JS-only deploy. Clear localStorage/sessionStorage, IndexedDB and Cache Storage, reload, wait ~20 s, reload again (repeat once if needed).
    • cci task run deploy can say "Succeeded" and deploy nothing (new field was missing). Use sf project deploy start --source-dir ... and verify with a query.
    • New fields need FLS. Admin sees nothing until UST_Portal_Widget_Admin is assigned.
    • Apex tests in the scratch org: ~80 pre-existing failures are environmental (Network is UnderConstruction; Alumni Community User profile and ETL User missing → "List index out of bounds"; Alumni_Business record type unavailable to admin). Not caused by code changes. Finish the config_dev flow to make them meaningful.
    • Jest + base component stubs: field-name/label are properties, not attributes — query all elements and filter on the property.

    Base-editor caveat to resolve¶

    The toolbar Image button stores pictures in Salesforce (rtaImage) rather than S3. Untested whether those render for guests on the portal, and they are not fast/public like S3. Decide in Phase 4: hide it, or confirm it works.

    Phase 0 — Page context: fix the mismatch and keep it current (design agreed 2026-10-15)¶

    Problem. ustWidgetZone derives the page context from CurrentPageReference (attributes.name, lowercased). Page_Context__c values are all, home, giving, events, profile, directory, news. Actual LWR page API names (from sfdc_cms__route): Home, alumni_directory__c, Alumni_Event_Creation__c, alumni_notes__c, business_directory__c, lawyer_search__c, my_account__c, My_Business__c, News_Detail__c, plus system pages (Login, Register, Error…). Only home matches; targeting a widget at "Directory" likely never matches.

    Platform facts (verified in dev org). Site pages cannot be listed at runtime: DigitalExperience is not queryable, no Tooling object exposes routes, NetworkPageOverride covers standard pages only. Only NavigationMenuItem is queryable (menu pages only). So the list must be built by the site itself.

    Where zones live today (from the repo bundle). body and sidebar are in individual page views (Home: body + sidebar; Alumni_Directory: sidebar). banner and above_footer are in the theme layout scopedHeaderAndFooter, i.e. on every page using that layout.

    Design: self-registering zone placements¶

    1. New object UST_Portal_Zone_Placement__c: Page_Name__c (lowercased page API name, or * for "all pages"), Zone__c, Scope__c (Page / Layout), Page_Label__c (admin-editable friendly label), Last_Seen__c, Hidden__c; unique external-id key Page|Zone.
    2. Layout-level zones (decided 2026-10-15): no bundle change. banner and above_footer live in the scopedHeaderAndFooter theme layout (layout type Inner, used by 14 views; only the two error pages use snaThemeLayout). That layout also holds the built-in LWR navigation components and ustAlumniTheme, so content placed there already appears on every page — keep using those zones for "every page" content. A zone cannot detect by itself whether it is in a shared layout, so the registry has an admin-editable Scope__c (Page / Layout). Seed banner and above_footer as Layout (Page_Name__c = *) from this verified fact; admins can flip the flag for any future layout zone. (Optional later: a zoneScope builder property on ustWidgetZone so the builder sets it automatically — would require editing/redeploying the theme layout file; not needed now.)
    3. Registration happens only in Experience Builder (state.app === 'commeditor', already detected in ustWidgetZone). The zone calls a non-cacheable Apex method that upserts the placement. Live visitors and guests never write; Apex also refuses unless the user can create the object. Zero overhead for the public site. A zone whose existing placement is Layout-scoped keeps * and is not duplicated per page when an admin visits different pages.
    4. Editor behavior (ustWidgetRecordEditor):
    5. Zone is chosen first; the page picker lists only pages that have that zone, plus All pages.
    6. Changing the zone auto-removes known pages that lack the new zone, with a notice and Undo ("Removed Directory — no Sidebar zone on that page").
    7. Pages not yet registered are kept with a warning (lets admins pre-configure before a page exists).
    8. "Appears on: Home, Alumni Directory" coverage line; warning when a widget would appear nowhere.
    9. Free-text escape hatch for unregistered page names.
    10. Page_Context__c becomes an unrestricted multi-select picklist so INCLUDES keeps working while the custom editor can save any page name. (Verify in the spike that the API/LWC accepts values not in the list.)
    11. Seed the registry once from the 16 routes/views in the current bundle (script or CCI task), and add a one-time data migration for existing widget records: directory → alumni_directory__c, etc. giving, events, profile, news are left as-is for now (no matching route in the dev bundle; owner to check whether those pages exist in EDA-Staging before mapping or retiring them).
    12. The same registry feeds the Portal link picker for buttons (Phase 3).

    Limits to remember¶

    • A zone removed in the builder is not detected (nothing runs). Show Last_Seen__c, flag stale entries, allow Hidden__c; do not delete automatically.
    • The registry reflects the builder state, which can be ahead of the published site.
    • Editor checks are advisory; records changed by data loader are not validated, and a mismatch simply means the widget does not render.
    • Unverified until built: that Apex DML works from the builder session, and unrestricted multi-select behavior.

    Steps¶

    1. Confirm the mismatch in the dev org (widget on a non-home page → expect no render).
    2. Build the object, permission sets (admin: create/edit; no guest access), registration Apex, seed of the layout zones, and tests (Apex: guest/non-admin cannot register, upsert idempotent, * handling; Jest: builder-only registration).
    3. Editor page/zone picker, auto-remove with Undo, coverage line.
    4. Picklist change, migration, seed, docs (WIDGET-CATALOG.md, MAIN_GUIDE.md, PortalWidgetController_TEST).

    Phase 1 — Spikes — DONE 2026-10-15¶

    All three answered against the dev org (spike component was temporary and has been removed).

    1. Insert text at the cursor — works (with one caveat)¶

    lightning-input-rich-text.insertTextAtCursor(text) (documented as "reserved for internal use"):

    Scenario Result
    Caret in the middle of text Inserted at the caret
    Focus moved to another control first (the real "Insert data tag" dropdown case) Still inserted at the last caret position
    Text selected Selection is replaced
    After insertion Editor fires change with the new HTML, so our wrapper, preview and save all see it; works inside a heading too

    Decision: use it for the rich-text "Insert data tag" dropdown, feature-detected (typeof editor.insertTextAtCursor === 'function'). Caveat: it is an internal-use API Salesforce could change. Fallback if it ever disappears: append the tag at the end of the content and tell the admin. The plain header field uses the supported lightning-input.setRangeText().

    2. Portal link resolution in the LWR site¶

    Observed in Experience Builder's live preview of the Alumni site (basePath = /alumni):

    Input NavigationMixin.GenerateUrl result
    standard__webPage /alumni-directory /alumni/alumni-directory (base path added)
    standard__webPage /alumni/alumni-directory /alumni/alumni-directory (not double-prefixed)
    standard__webPage /news/abc?x=1#top /alumni/news/abc?x=1#top (query and hash kept)
    standard__webPage / /alumni/
    standard__webPage https://www.stthomas.edu unchanged
    standard__webPage //evil.example.com/x unchanged — protocol-relative, an open-redirect risk
    standard__webPage javascript:, mailto:, tel: mangled to /alumnijavascript:..., /alumnimailto:...
    comm__namedPage My_Business__c, Home, alumni_directory__c resolves to the page
    comm__namedPage my_business__c, home (lowercase) fails silently: redirects to /alumni/?redirectPageContext=... (home)
    comm__namedPage unknown page same silent redirect — no error
    Raw <a href="/alumni-directory"> points at the domain root, would 404 — not usable

    Page names for comm__namedPage are case-sensitive and our registry stores them lowercased, so they cannot be used to build links. (Not tested: clicking, because the Builder overlay intercepts clicks, and a published site; Navigate uses the same resolution as GenerateUrl.)

    Decisions for Phase 3: - Portal links are stored as relative paths (/alumni-directory, /news/abc), resolved with GenerateUrl({ type: 'standard__webPage', attributes: { url } }). The base path is added at render time, so the same JSON works in sandbox and prod even if the prefix differs. Do not use comm__namedPage. - Render a real <a href={generatedUrl}> and call Navigate on click for single-page navigation. - Validation (save-time in the editor, re-checked in Apex, and again at render): portal path must match ^/(?!/)[^\s]*$ — starts with exactly one /, no scheme, no whitespace. Reject //. - mailto: and tel: must not go through GenerateUrl — render them as plain href after allowlisting. External links: https: only.

    3. Page picker source¶

    • Site pages cannot be listed at runtime (confirmed earlier). NavigationMenuItem can be queried via SOQL and is scoped by NavigationLinkSet.NetworkId.
    • Columns of interest: Label, Type (InternalLink = page with a path, MenuLabel = group heading, NavigationalTopic = skip), Target (relative path such as /alumni-directory), Status (Draft or Live — this dev site is unpublished, so rows are Draft; a published site has both), and AccessRestriction (LoginRequired or None, a useful hint for guest-visible buttons).
    • Link set names differ per org (Default_Navigation2 here; sync_navigation_menu handles that), so scope by the site's network, not by developer name.
    • The zone registry cannot supply link paths (it stores page API names, not URL paths).

    Decision: the Portal-link picker offers site menu pages (deduplicated by Target, preferring Live, labelled with a "login required" note) plus free typing of any relative path. Implement as a small Apex method (getPortalLinkSuggestions) that finds the network by name (Alumni, the same name sync_navigation_menu uses; make it configurable) and returns [{label, path, loginRequired}].

    Phase 2 — Data tags¶

    Tag registry (single source of truth, Apex)¶

    Tag Source Allowed in URLs
    First_Name Nickname__c, else First_Name_Text__c no
    Last_Name Last_Name_Text__c no
    Class_Year Class_Year_Text__c no
    Employer Employer_Text__c no
    Job_Title Occupation_Text__c no
    St_Thomas_Degree St_Thomas_Degree_text__c no
    City_State City_State__c no
    Contact_Id Contact_ID__c (formula) yes
    Banner_ID Contact_Banner_ID__c (formula) yes

    Excluded on purpose: email, phone, mobile, birthdate, mailing street/postal code/country, middle name. Registry is exposed via an @AuraEnabled method (label, token, sample value) so the editor dropdown and the Apex resolver cannot drift.

    Behavior¶

    • Syntax {{ Name }} or {{ Name|fallback }}. Case-insensitive; spaces ≡ underscores (matches the existing EASY/VF behavior in ApplicationUtilities.replaceDataTags).
    • Strict pattern that tolerates editor formatting inside a tag ({{First_<b>Name</b>}}): match \{\{((?:[^{}<]|<[^>]*>)+?)\}\}, strip tags from the capture, then parse name/fallback.
    • Blank value → fallback if given, else empty string. Guests and users with no directory record get blanks/fallbacks. Unknown tags are left literally in the text (and flagged to admins in the editor).
    • Escape every substituted value. (The VF implementation inserts values unescaped; alumni can edit these fields themselves.) Body = HTML-escaped; header and button labels = plain text (no escaping, the LWC template escapes on render); URLs = URL-encoded. Fallback text is inserted as-is (URL-encoded in URLs): the admin wrote it in the same format as the surrounding text and the editor has already HTML-encoded it, so escaping it again would double-encode characters such as &.
    • In URLs: only tags marked "allowed in URLs" resolve, values are URL-encoded; other tags in a URL resolve to empty.
    • Resolve server-side in PortalWidgetController for the current user's Alumni_Directory__c (Contact__c = running user's ContactId), using a separate system-mode query of only the whitelisted fields. Do not add fields to the existing WITH USER_MODE directory query — a missing FLS on any new field would break the whole widget zone for portal users.
    • Applies to: Static_Content_Header__c, Static_Content__c, button labels and button URLs (and hero text later).

    Editor UX¶

    • "Insert data tag" dropdown beside Paragraph style (rich text; uses insertTextAtCursor, feature-detected — Phase 1 spike 1) and beside the header input (plain input; see "as built" for why it splices the value).
    • Live warnings for unknown tag names.
    • Preview resolves tags with sample values from the registry.
    • Stretch: "Preview as" a chosen Alumni Directory record.

    Tests¶

    Apex: parsing (formatted/split tags, case, spaces), fallback, blank, guest, escaping (<script> in a value), URL encoding, URL-disallowed tags, unknown tags. Jest: insert dropdown, unknown-tag warning.

    Phase 3 — Call-to-action buttons¶

    Data model¶

    • Buttons_JSON__c — Long Text Area (32,768) on UST_Portal_Widget__c.
    • Button_Placement__c — picklist: Below (default), Above.
    • Add both to UST_Portal_Widget_Admin and Alumni_Portal_Guest_User permission sets.

    JSON shape (versioned)¶

    {
  "version": 1,
  "buttons": [
    {
      "id": "b1",
      "label": "Give today, {{First_Name|friend}}",
      "type": "external",
      "url": "https://example.edu/give?id={{Contact_Id}}",
      "newTab": true,
      "style": "brand",
      "align": "left",
      "icon": "utility:heart"
    },
    { "id": "b2", "label": "Alumni Directory", "type": "portal", "url": "/alumni-directory", "style": "outline-brand", "align": "left" }
  ]
}

    Styles carried over from EASY Widget Button: text_link, brand, outline-brand, destructive, text-destructive, neutral, success. Alignment: left, center, end. Icon is optional and validated. No per-button size — sizing comes from the widget content CSS class.

    Link rules (enforced at save AND at render; Apex re-validates) — updated by Phase 1 spike 2¶

    • External: https: only. New tab → rel="noopener noreferrer".
    • Email / phone: mailto: and tel: are allowed but rendered as plain hrefs (never through GenerateUrl, which mangles them).
    • Portal: stored as a relative path (/alumni-directory, /news/abc?x=1), validated with ^/(?!/)[^\s]*$ (exactly one leading /, no scheme; //host is rejected as an open redirect). Resolved at render with NavigationMixin.GenerateUrl using standard__webPage, which adds the site base path (/alumni here) — so the JSON is portable between sandbox and prod. Never use comm__namedPage (case-sensitive, fails silently) or a raw href="/path" (would 404 at the domain root).
    • Picker suggestions come from the site menu (NavigationMenuItem, see Phase 1 spike 3); any relative path can also be typed.
    • Render real <a> elements (not <button>), call Navigate on click for single-page navigation, visible focus, decorative icons, unique labels.

    Components¶

    • ustWidgetButtonEditor (child of ustWidgetRecordEditor): add / edit / reorder / delete, saves with the record's Save (EASY writes immediately and cannot edit). Uses stable ids, not array index. Section shown for widget types that support buttons (extend COMPONENT_SECTIONS).
    • ustWidgetButtons (shared renderer): used by ustStaticContent now and the hero widget later.
    • Apex: parse/validate/sanitize JSON, drop invalid entries, resolve tags in label/url, return a clean list on PortalWidgetDto.
    • Button size is its own picklist, Button_Size__c, separate from Content_CSS_Class__c, so a panel style and a button size can be combined (resolved during the build; see "as built").

    Tests¶

    Apex: JSON sanitization, scheme allowlist, relative path rules, tag resolution in labels/URLs. Jest: editor add/edit/reorder/delete, renderer placement above/below, unsafe URL rejection.

    How it behaves. Buttons are stored as versioned JSON and rewritten by Apex on every read: tags resolved (links: identifier tags only, URL-encoded), invalid buttons silently dropped, unknown style/alignment/icon fall back to defaults, label capped at 80 characters, portal links never open a new tab, only https: links do. The editor and the server enforce the same rules, but the server never trusts the editor.

    Findings that shaped the build (do not rediscover). - lightning-record-edit-form only returns fields it is asked for (an input field on the form) or that are on the page layout. Buttons_JSON__c has no input, so after a reload the editor showed no buttons even though they were saved. Fix: an always-present hidden lightning-input-field for it in ustWidgetRecordEditor.html. Any future field edited by a custom component needs the same. - NavigationMixin.GenerateUrl must not run before the component is connected. The parent assigns buttons before attaching the child, so resolving in the setter silently failed and the portal link had no href in the real site (the editor preview could not show this because preview mode skips resolution). The renderer now resolves from connectedCallback and when buttons change afterwards. Two Jest tests fail against the old code. - Jest: mocking lightning/navigation with { virtual: true } makes the mock unreliable when the whole suite runs (passes alone, fails in the full run). Omit virtual: true for that module. - Jest: base-component stubs expose name / type as properties, not attributes (filter on the property). - Link regexes with control characters are built from strings (new RegExp) so no inline ESLint disable is needed; the generated pattern was checked against tab, DEL, U+0001, and backslash cases. - The page-picker list shows 8 entries in the dev org (Home + the 7 menu pages) with a "login required" note; suggestions are only returned to users who can edit widgets, so portal users never see site structure.

    Known limits / follow-ups. - Buttons sit above or below the text only, not inside a paragraph. - Only external https/mailto/tel and portal paths exist as types (no event-registration or giving types yet). - The portal link menu comes from NavigationMenuItem for the network named Alumni (PortalButtons.SITE_NETWORK_NAME); change it there if the site is renamed. Pages not in the menu can be typed in by path. - Not tested: a published site with real guest traffic (caching of personalized buttons), and keyboard/screen reader behaviour beyond the semantics built in (real links, assistive "opens in a new tab" text, focus ring). - PortalWidgetController.getWidgetsForZone and a few helpers exceed Code Analyzer complexity thresholds (Moderate); not changed.

    How the S3 tool really behaves (read from the deployed source; do not rediscover)¶

    • File key = md5(orgId + recordId) + fileNameSuffix + extension. A null suffix becomes the literal text null (verified in Apex), and the later lookup searches hash. and never finds it, so the editor always passes a suffix: -hero (desktop) and -hero-mobile (mobile).
    • It writes the image URL to the record field itself (its own Apex update, in user mode, needs Read/Edit FLS on that field) and then fires a RefreshEvent (lightning__refresh). It never reports the URL to the parent. So the hero URL fields are not inputs on the record form (a later Save would overwrite the fresh URL with the form's stale copy); the editor reads them with getRecord and refreshes with notifyRecordUpdateAvailable when the refresh event arrives.
    • Resizing happens in the browser (canvas) with image-max-width / image-max-height and image-mode crop or resize; output is always PNG. It needs an existing record (a new, unsaved widget has no Id).
    • Only users with the dependency's AWS_S3_Directory_Image permission set can upload. Our permission set cannot include it (it lives in the dependency), so widget admins need both. config_dev already assigns it to System Administrators.
    • The dependency component is not in this repo; it must be installed in an org before our templates that reference c-aws-s3-directory-image will deploy (CumulusCI does this through cumulusci.yml dependencies).

    Record sharing (added after Phase 4). UST_Portal_Widget__c has an external default of Private, so signed-in portal users and the site guest could not read widget records directly (only through the without sharing controller). There are now two rules, both Read-only and both limited to Is_Active__c = true: - ShareActiveWidgetsWithPortalUsers shares with All Customer Portal Users (signed-in portal users). Lives in force-app/main/default/sharingRules/UST_Portal_Widget__c.sharingRules-meta.xml. - ShareActiveWidgetsWithAlumniGuest shares with the Alumni site guest user (community nickname Alumni). Lives in unpackaged/config/guestSharing/ and is deployed by the task create_community_guest_sharing (config_dev step 5.7), not with force-app. A guest rule fails to deploy ("Specify a guest user's nickname for the guestUser field", reproduced) until the site and its guest user exist, and force-app is deployed before create_community; keeping it in force-app would have broken every fresh cci flow run dev_org. The folder is raw metadata format (package.xml plus sharingRules/<Object>.sharingRules, no -meta.xml). For EDA-Staging or production, deploy that folder after the site exists.

    Why: widgets are published content, and the pictures a Hero Banner points at must load for guests. Widgets hold no personal data: data tags ({{First_Name}} and so on) are stored as plain text and only resolved per viewer at render time, so a viewer who reads the record directly (for example through an Aura endpoint) sees the tag, not anyone's data. Do not type real personal details into widget text. Turning a widget off removes the share; turning it on adds it (checked in the dev org: 18 active widgets, 18 shares per rule, 0 for the inactive one, and a toggle added then removed both rows). Field access is still limited by the Alumni_Portal_Guest_User permission set.

Candidate changes in the tool repo: JPEG ~0.85 for photos, a versioned file name, and a second size. - Inline images in Static Content are still not supported (see the decision above). - A hero is as wide as its zone; full-bleed width depends on where the zone sits in the page template. - The alt-text rule blocks Save when a picture exists; a "decorative image" option could be added if needed.
